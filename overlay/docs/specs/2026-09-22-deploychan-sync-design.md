# Синк каталога deploychan — дизайн

Дата: 2026-09-22. Статус: на ревью у владельца.
Второй из двух каналов наполнения. Первый (переезд с машины) уже реализован.

## Цель

`overlay/harness.sh sync` тянет паки из MCP deploychan и кладет их в
`overlay/skills/`, откуда раскатка разносит их по машинам наравне с переехавшими
и апстримными скиллами. Каталог Кисы перестает быть чем-то, что надо
переписывать руками.

## Место в карте каналов

| | Канал 1: переезд | Канал 2: синк |
|---|---|---|
| Природа | разовая, локальная | повторяемая, сетевая |
| Источник | `~/.claude/skills` этой машины | MCP deploychan |
| Команда | `harness.sh capture` | `harness.sh sync` |
| Спек | `2026-09-21-skill-capture-design.md` | этот |

Оба кладут в `overlay/skills/`. Понятие происхождения скилла, введенное
переездом (файл `.harness-origin`), синк использует и расширяет.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Где живет синк | Отдельная команда; `plan` и `apply` остаются оффлайновыми |
| Состав дистрибутива | Committed-файл `overlay/sync.conf`, а не профиль |
| Природа пака | Объявляется в `sync.conf`, из тела не выводится |
| Текстовый пак | Материализуется в `overlay/skills/<id>/SKILL.md` |
| Софтовый пак | Клонируется вне репозитория; установщик не запускается |
| Конфликты | Хэш в маркере отличает обновление каталога от локальной правки |
| Клиент к MCP | Python stdlib, только для `sync` |

## Границы: что ходит в сеть

Синк — единственное, что обращается к сети. Это сознательная граница: `plan` и
`apply` сохраняют свойство «что показал `plan`, то и сделает `apply`», которое
сетевой вызов разрушил бы.

Следствие для второй машины: там синк не нужен. Результат коммитится, и скиллы
приезжают из репозитория.

## Команда

```
overlay/harness.sh [plan|apply]            # раскатка
overlay/harness.sh capture [plan|apply]    # переезд с машины
overlay/harness.sh sync [plan|apply]       # синк каталога, по умолчанию plan
```

`sync plan` ходит в сеть, показывает решение по каждому паку и не пишет ничего.
`sync apply` записывает. Синк пишет только в `overlay/skills/` и в каталог
клонов; домашние каталоги рантаймов он не трогает ни в одном режиме.

## Состав дистрибутива

`overlay/sync.conf` — в git, одинаков на всех машинах. Пустые строки и строки,
начинающиеся с `#`, игнорируются.

```
# Текстовый пак: одно поле - идентификатор из каталога.
x-content-advisor

# Софтовый пак: идентификатор, URL репозитория, закрепленная ревизия.
zaebal  https://github.com/howdeploy/Z.A.E.B.A.L.git  v1.2.0
```

Одно поле в строке — текстовый пак. Три поля — софтовый. Любое другое число
полей — `E_PROFILE` с номером строки.

Файл лежит в репозитории, а не в `profile.env`, потому что состав дистрибутива —
свойство репозитория, а не машины: результат синка коммитится, и на второй
машине профиля может не быть вовсе, а скиллы там появятся.

### Почему природа пака объявляется, а не выводится

Тело пака `zaebal` содержит строку `git clone https://github.com/howdeploy/Z.A.E.B.A.L.git`
посреди markdown, рядом с тремя другими ссылками на файлы того же репозитория.
Вытащить адрес оттуда можно только разбором прозы. Это нарушило бы инвариант
«не угадывать» и сломалось бы при первой же правке текста Кисой. Поэтому адрес
и ревизия объявляются владельцем, а не извлекаются.

## Текстовая ветка

Пак материализуется в `overlay/skills/<id>/SKILL.md`. Фронтматтер синтезируется
из полей MCP в конвенции апстрима — она сверена по всем 11 скиллам `skills/`:
там везде есть `name`, `description` и `metadata.hermes.tags`.

```
---
name: <id>
description: "<summary одной строкой>"
metadata:
  hermes:
    tags: [<tags через запятую>]
  deploychan:
    triggers: [<triggers>]
    reminder: "<reminder>"
---
<body пака как есть>
```

Имя каталога и значение `name:` — это `id` пака, как у апстрима, где `name`
совпадает с именем каталога. Человекочитаемое `name` из MCP не теряется: оно и
так стоит первым заголовком тела.

`summary` и `reminder` приводятся к одной строке: переводы строк заменяются
пробелами, внутренние двойные кавычки экранируются. Поля `triggers` и `reminder`
уходят под `metadata.deploychan`, потому что в формате скиллов для них нет
штатного места, а терять их не хочется: `triggers` помогают рантайму выбрать
скилл. Поле `allowed_tools` не переносится — в паках каталога оно пустое, и
класть в файл пустой ключ незачем.

Тело пака не редактируется. Все, что делает синк, — перекладывает поля.

## Софтовая ветка

Софтовый пак не материализуется как скилл. Синк клонирует объявленный
репозиторий в `~/.kisa-harness/src/<id>` и переключает его на закрепленную
ревизию. Каталог клонов лежит вне репозитория и в git не попадает.

Команда установки печатается в список «Сделать вручную». Харнес не запускает
чужой установщик: у `zaebal` это Python-скрипт, который правит `~/.codex/hooks.json`,
и решение его выполнить принимает человек.

Настоящий скилл при этом не теряется — он лежит внутри клона, вместе с рантаймом,
без которого все равно не работает.

Состояния:

- клона нет — `sync apply` клонирует и переключает на ревизию;
- клон на нужной ревизии — ничего не делается;
- клон на другой ревизии — `sync apply` подтягивает и переключает;
- в клоне есть локальные изменения — синк его не трогает и предупреждает.

Последний случай — предупреждение, а не ошибка: один испорченный клон не должен
останавливать синк остальных паков.

## Происхождение и конфликты

Синк пишет в `overlay/skills/<id>/.harness-origin` одну строку:

```
deploychan:<id> sha256:<хэш> <YYYY-MM-DD>
```

Формат тот же, что завел переезд, — `<источник> <детали>`.

Хэш — это sha256 содержимого файла `SKILL.md`, которое синк сгенерировал в тот
раз. При следующем запуске синк генерирует файл заново из текущего каталога и
сравнивает лежащий на диске файл с записанным хэшем:

| Диск против хэша | Новый файл против диска | Что делает синк |
|---|---|---|
| совпал | совпал | `same`, ничего не пишет |
| совпал | отличается | `updated`, показывает дифф, пишет |
| разошелся | — | `edited`, показывает дифф, **не пишет** |

Третий случай означает, что файл правили руками. Синк его не перезаписывает
молча; чтобы принять обновление, файл удаляют и синкают заново.

Отдельно — случай, когда каталог `overlay/skills/<id>` существует, но пришел не
из синка: маркера нет вовсе или в нем другой источник. Так бывает, если скилл с
тем же именем переехал с машины. Синк такой каталог не трогает и сообщает
`foreign`. Чей это скилл, решает владелец: либо переименовывает свой, либо
убирает пак из `sync.conf`. Автоматически угадывать тут нечего.

Хэш считается в Python, единственном месте, где он читается и пишется. Это не
защита от подмены — это отличение «каталог обновился» от «я правил».

## Клиент к MCP

`overlay/lib/sync.py`, только стандартная библиотека, вызывается исключительно
режимом `sync`. Ядро `plan`/`apply` остается чистым bash: инвариант не
отменяется, а сужается до «ядро без Python».

Выбор обоснован не языком HTTP-запроса — TLS одинаков везде, — а тем, что
`urllib` проверяет сертификаты сам и разбирает JSON штатным парсером. Тот же
клиент на `curl` и `jq` пришлось бы собирать из конвейеров, а этот класс ошибок
в проекте уже стрелял трижды: обертка `jqx` из-за CRLF и порчи путей, `grep`
по `\r`, несплитящийся список в профиле.

Скрипт получает адрес сервера из переменной. Если задана `HARNESS_MCP_FIXTURE`,
он читает каталог из указанного JSON-файла вместо сети — так синк покрывается
тем же раннером, что и остальное, без сетевых вызовов в тестах.

## Дисциплина ревью

Синканный пак — не данные, а поведение: он становится `SKILL.md`, попадает в git
и раскатывается в три рантайма на всех машинах, после чего агент ему следует.

Отсюда правило, которое стоит держать в голове при каждом синке: **дифф
синканного `SKILL.md` смотрится как код, а не как текст**. Это единственное
место, где видно, какие инструкции получит агент, прежде чем они начнут
действовать. Механика к этому подводит — синк показывает дифф до записи, а `git
diff` показывает его второй раз перед коммитом, — но само сравнение делает
человек.

## Ошибки

Один новый код:

- `E_MCP` — сервер недоступен, ответ не разобран, объявленный пак в каталоге не
  найден. При любой такой ошибке синк не пишет ничего.

Существующий `E_PROFILE` покрывает и `overlay/sync.conf`: это тоже написанная
владельцем конфигурация, и сообщение называет файл и номер строки.

Сбой `git clone` или `git checkout` не роняет синк целиком: пак уходит в
предупреждение и в список «Сделать вручную», остальные обрабатываются.

## Вывод

Строки статуса начинаются с ASCII-токена, как во всем харнесе:

```
SYNC    x-content-advisor: new
SYNC    comfyui-prompt-craft: same
SYNC    obsidian-dataweave: updated
SYNC    xrayebator: edited
SYNC    obsidian-dataweave: foreign
SYNC    zaebal: софт, ревизия v1.2.0
SKIP    telegram-custom-emoji-mosaic: нет в sync.conf
WROTE   overlay/skills/x-content-advisor
CLONED  ~/.kisa-harness/src/zaebal -> v1.2.0
WARN    в клоне zaebal есть локальные изменения, не трогаю
```

Строки `SKIP` перечисляют паки, которые есть в каталоге, но не объявлены в
`sync.conf`. Это способ узнать, что вообще предлагает Киса, не читая каталог
отдельно.

## Тесты

Дополняют `overlay/tests/run.sh`, в том же стиле: свежий `HOME` из `mktemp -d` на
кейс, каталог берется из фикстуры через `HARNESS_MCP_FIXTURE`, клоны — из
локального репозитория через `HARNESS_SRC_DIR`.

1. Текстовый пак материализуется: каталог, `SKILL.md`, фронтматтер с `name`,
   `description` и тегами.
2. Многострочный `summary` приводится к одной строке, кавычки экранированы.
3. `triggers` и `reminder` попадают под `metadata.deploychan`.
4. Повторный `sync apply` без изменений в каталоге ничего не меняет (`same`).
5. Изменившийся в каталоге пак обновляется (`updated`), маркер получает новый хэш.
6. Файл, правленный руками, не перезаписывается (`edited`), дифф показан.
7. `sync plan` не создает и не меняет ни одного файла.
8. Пак из каталога, не объявленный в `sync.conf`, дает строку `SKIP`.
9. Объявленный пак, которого нет в каталоге, дает `E_MCP`.
10. Строка `sync.conf` с двумя полями дает `E_PROFILE` с номером строки.
11. Софтовый пак клонируется на объявленную ревизию, `SKILL.md` для него не
    создается, команда установки попадает в «Сделать вручную».
12. Клон с локальными изменениями не трогается, синк продолжает работу.
13. Недоступный сервер дает `E_MCP`, ни один файл не записан.
14. Синк не трогает `~/.claude/skills` и `~/.codex/skills` ни в одном режиме.
15. Каталог скилла без маркера синка (например, переехавший с машины) не
    перезаписывается и дает `foreign`.

## Риски

1. **Синканный пак — это инструкции, которым агент подчиняется.** Смягчение —
   дифф до записи, `git diff` до коммита и явное правило ревью выше. Полностью
   риск не убирается: он в природе канала.
2. **Python становится нужен тому, кто синкает.** На машине владельца есть
   3.14.5. На машине без Python синк не запустится, но раскатка — да, потому что
   результат приезжает из репозитория.
3. **Ревизия софтового пака закрепляется вручную.** Обновление требует правки
   `sync.conf`. Это цена за воспроизводимость клона.
4. **Формат ответа MCP не зафиксирован контрактом.** Поля сверены по живому
   каталогу на 2026-09-22 (`id`, `name`, `summary`, `reminder`, `tags`,
   `triggers`, `allowed_tools`, `body`). Изменится форма ответа — синк упадет с
   `E_MCP`, а не запишет мусор.

## Вне объема

- Скелет вики и FTS5, guard и RTK — отдельные подпроекты.
- Запуск чужих установщиков.
- Автоматическое обновление закрепленных ревизий.
- Удаление из `overlay/skills/` паков, убранных из `sync.conf`: синк только
  добавляет и обновляет.
- Синк правил и настроек — канал носит только скиллы.
