# Переезд скиллов на харнес — дизайн

Дата: 2026-09-21. Статус: на ревью у владельца.
Первый из двух каналов наполнения. Второй (синк каталога deploychan) получит свой спек.

## Цель

Одна команда переносит личные скиллы с этой машины в `overlay/skills/`, после чего
харнес разносит их по всем машинам наравне со скиллами апстрима. Слой перестает быть
пустым.

Сегодня каркас работает, но раздает только чужое: 11 скиллов апстрима и правила Кисы.
`overlay/skills/` пуст, `overlay/rules/*.md` пусты. Поставь харнес на вторую машину —
там появится Киса, но не появится владелец.

## Карта каналов

Наполнение слоя идет двумя каналами разной природы:

| | Канал 1: переезд | Канал 2: синк каталога |
|---|---|---|
| Природа | разовая, локальная | постоянная, сетевая |
| Источник | `~/.claude/skills` этой машины | MCP deploychan |
| Команда | `harness.sh capture` | `harness.sh sync` |
| Спек | этот | отдельный |

Оба кладут в `overlay/skills/`, поэтому вводимое здесь понятие происхождения скилла
нужно обоим.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Природа переезда | Разовый переезд, а не двусторонняя синхронизация. После переезда источник истины — репозиторий |
| Отбор | Денилист: берем все, кроме отклоненного |
| Кто наполняет денилист | Автозасев по доказуемым признакам плюс ручные дополнения в профиле |
| Откуда берем | Только Claude Code (`CAPTURE_FROM`), без слияния между рантаймами |
| Секреты | Файлы `.env` не переезжают никогда |

## Почему разовый переезд, а не синхронизация

Харнес ставит `overlay/skills/*` в `~/.claude/skills/`. Обратное движение тех же
файлов замкнуло бы кольцо и потребовало правил разрешения конфликтов. Разовый переезд
кольца не создает: после него правки делаются в репозитории, а `apply` разносит их по
машинам. Это же означает, что локальная правка уже переехавшего скилла обратно не
подбирается — см. правило D3.

## Команда

```
overlay/harness.sh [plan|apply]            # раскатка, как сейчас
overlay/harness.sh capture [plan|apply]    # переезд, по умолчанию plan
```

Грамматика сохраняет главное свойство: `plan` ничего не пишет и показывает, что
произойдет. `capture plan` печатает решение по каждому скиллу и выходит; `capture apply`
копирует отобранное в `overlay/skills/`.

Переезд пишет только внутрь репозитория. Домашние каталоги рантаймов он читает, но не
меняет — ни в одном из режимов.

## Отбор: денилист с автозасевом

Кандидаты — каталоги в `$(runtime_home "$CAPTURE_FROM")/skills`, содержащие `SKILL.md`.
Запись без `SKILL.md` не скилл и пропускается (в этом каталоге лежит, например,
`README.md`).

Кандидат отклоняется по первому сработавшему правилу:

| Правило | Признак | Почему |
|---|---|---|
| D1 | Имя совпадает с каталогом в `$UPSTREAM_DIR/skills/` | Доказуемо апстрим. Захват заморозил бы его: скилл из `overlay/` замещает одноименный апстримный, и `git pull upstream` перестал бы на него влиять |
| D2 | В значении `description:` фронтматтера есть `(gstack)`, без учета регистра | Приходит из своего маркетплейса и обновляется через `/gstack-upgrade` |
| D3 | Имя уже есть в `$OVERLAY_SKILLS_DIR` | Уже управляется харнесом: переехало раньше или пришло синком |
| D4 | Имя перечислено в `CAPTURE_DENY` профиля | Ручное решение владельца |

Все остальное переезжает.

На машине владельца на 2026-09-21 это дает: 11 отклонений по D1, 50 по D2, и примерно
пять кандидатов — `goal`, `learn`, `product-editor`, `uniqore-cpo`,
`uniqore-desktop-test` — плюс три спорных (`gstack-upgrade`, `open-gstack-browser`,
`setup-deploy`), которые владелец либо выпишет в `CAPTURE_DENY`, либо оставит.

### Почему признаки именно такие

D1 — это сравнение имен с деревом апстрима, факт, а не догадка. D2 опирается на метку
в описании, и это единственный хлипкий признак в спеке. Он выбран сознательно и смещен
в безопасную сторону: ошибочное отклонение стоит дешево (скилл просто не переехал,
владелец видит строку с причиной и правит), ошибочный захват стоит дорого (чужой скилл
молча вмерзает в слой и перестает обновляться). Поэтому при сомнении — отклоняем.

Проверка идет по значению `description:`, а не по всему файлу: скилл, упоминающий gstack
в теле, не должен отклоняться из-за этого.

### Принудительный захват

Форк апстримного скилла в свой слой (намеренное замещение) этим спеком не
поддерживается. Нужен — копируется руками; это осознанное действие, и оно не должно
прятаться за флагом.

## Секреты не переезжают

`overlay/skills/` коммитится в git. README апстрима велит класть `.env` с ключом EvoLink
рядом со скриптами `suno-music`, и такие файлы встречаются и в личных скиллах. Переезд
исключает любой файл с именем `.env` на любом уровне вложенности и печатает
предупреждение о каждом пропущенном.

Это не защита от всех секретов — только от самого вероятного их места. Владелец смотрит
дифф перед коммитом, как обычно.

## Происхождение

Каждый переехавший скилл получает файл `.harness-origin` с одной строкой:

```
capture <имя-машины> <YYYY-MM-DD>
```

Имя машины берется из `${HOSTNAME:-unknown}` (переменная bash), дата — из `date`. Новых
зависимостей это не добавляет: команды `hostname` в списке пререквизитов нет и не
появится.

Он документирует, откуда скилл взялся, когда через полгода возникнет вопрос. Синк будет
писать сюда свой формат (`deploychan:<id>@<revision>`), поэтому формат — одна строка
`<источник> <детали>`, а не структура.

Маркер попадает в `overlay/skills/<имя>/` и оттуда, вместе со скиллом, в каталоги
рантаймов. Рантайму он безразличен: это не `SKILL.md`.

## Идемпотентность

Повторный `capture apply` без изменений не создает и не меняет ни одного файла: все, что
переехало, отклоняется правилом D3.

Следствие, которое надо понимать: правка переехавшего скилла в `~/.claude/skills`
обратно не подбирается. После переезда правки делаются в репозитории.

## Вывод

Строки статуса начинаются с ASCII-токена, как и в остальном харнесе:

```
CAPTURE uniqore-cpo
CAPTURE product-editor
DENY    researcher: апстрим
DENY    browse: метка gstack
DENY    open-gstack-browser: профиль
DENY    learn: уже в overlay
SKIP    README.md: нет SKILL.md
WARN    в uniqore-cpo пропущен .env: секреты не переезжают
```

В режиме `apply` добавляется `WROTE   overlay/skills/<имя>` на каждый перенесенный скилл.

## Профиль

Новые ключи, оба необязательные:

| Ключ | Дефолт | Смысл |
|---|---|---|
| `CAPTURE_FROM` | `claude` | Из какого рантайма забирать. Значения: `claude`, `codex`, `hermes` |
| `CAPTURE_DENY` | пусто | Имена через пробел, которые не переезжают |

`CAPTURE_FROM` берет ровно один рантайм: скиллы с одинаковым именем в разных рантаймах
могут отличаться, и молча выбирать один из них — угадывание.

## Ошибки

- Каталога скиллов у выбранного рантайма нет — сообщение и выход 0. Нечего переносить не
  значит сбой.
- `CAPTURE_FROM` не из списка — `E_PROFILE`.
- Новых кодов ошибок спек не вводит.

## Тесты

Дополняют `overlay/tests/run.sh`, в том же стиле: свежий `HOME` из `mktemp -d` на кейс.

1. Личный скилл переезжает в `overlay/skills/` целиком, со вложенными файлами.
2. Скилл с именем из `skills/` апстрима отклонен по D1.
3. Скилл с `(gstack)` в описании отклонен по D2.
4. Скилл, уже лежащий в `overlay/skills/`, отклонен по D3.
5. Имя из `CAPTURE_DENY` отклонено по D4.
6. Каталог без `SKILL.md` пропущен.
7. `.env` не переехал, в выводе есть предупреждение.
8. `capture plan` не создает ни одного файла в `overlay/skills/`.
9. Повторный `capture apply` не меняет ни одного файла.
10. У переехавшего скилла есть `.harness-origin` с префиксом `capture`.
11. Обычные `plan` и `apply` продолжают работать: грамматика команд не сломана.

## Риски

1. **Метка `(gstack)` — единственный хлипкий признак.** Маркетплейс может перестать ее
   ставить, и тогда его скиллы начнут считаться личными. Смягчение: вывод показывает
   причину по каждому скиллу, а решение принимает человек, глядя на список.
2. **`overlay/skills/` перестает быть только своим.** После переезда в нем смешаны
   личные скиллы и (позже) синканные. Различает их `.harness-origin`.
3. **Размер слоя.** Переехавшие скиллы попадают в git со всем содержимым, включая
   бинарные вложения, если они там есть. Владелец видит дифф перед коммитом.

## Вне объема

- Синк каталога deploychan — отдельный спек.
- Принудительный захват апстримного скилла.
- Переезд правил (`overlay/rules/*.md`) и настроек.
- Захват из Codex и Hermes одновременно с Claude Code.
- Обратная синхронизация правок после переезда.
